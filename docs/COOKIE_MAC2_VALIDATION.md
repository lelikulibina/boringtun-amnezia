# Проверка cookie/MAC2 совместимости

Этот документ фиксирует алгоритм, реализованный в Rust packet codec, и набор обязательных проверок перед заявлением полной совместимости.

## Направление клиент → сервер

1. Клиент получает Cookie Reply и расшифровывает его ключом, производным от публичного ключа сервера.
2. Cookie сохраняется для следующего handshake.
3. При H1/H2 randomization клиент вычисляет MAC1 по фактическому рандомизированному заголовку, затем MAC2 по сообщению с этим MAC1.
4. Сервер проверяет MAC1 и MAC2 до канонизации заголовка.

## Направление сервер → клиент

1. При выдаче Cookie Reply сервер извлекает cookie с помощью ключа, производного от собственного публичного ключа, и AAD MAC1 принятого handshake.
2. При получении следующего handshake сервер проверяет исходные MAC1 и MAC2.
3. Если MAC2 валиден, после канонизации заголовка сервер пересчитывает MAC1 и MAC2 для неизменённого BoringTun RateLimiter.
4. Если MAC2 невалиден, кодек не исправляет его: BoringTun должен отправить новый Cookie Reply.

## Проверки

- MAC1 и MAC2 round-trip при рандомизированном H1.
- Невалидный MAC2 не становится валидным после канонизации.
- Cookie Reply decrypt с обоими направлениями ключей и обоими вариантами AAD (randomized/canonical MAC1).
- Ложный handshake-кандидат не перехватывает transport datagram.
- Внешняя двусторонняя проверка с закреплённым amneziawg-go обязательна перед релизом.

## Ограничение

Unit-тесты подтверждают внутреннюю согласованность Rust-кода, но не заменяют interoperability-тесты с официальной Go-реализацией и проверку ротации cookie по времени/IP.
